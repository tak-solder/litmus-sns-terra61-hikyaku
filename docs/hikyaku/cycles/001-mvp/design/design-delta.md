# 設計差分

## このサイクルで作るもの

新規開発で、既存の本番データは無い。すべてのテーブル・エンドポイントは追加のみで、旧形式の撤去や移行は発生しない。

### 全体構成

ブラウザ・モバイルは、ALB 越しに同一オリジンで `/api/*` を api サービス、それ以外を web サービスへ振り分ける。web（Next.js）は BFF で、ブラウザは api を直接呼ばない。画面の表示は Server Components、クライアント発の操作（続きの読み込み、いいね、フォロー、投稿など）は Server Actions が受け、web のサーバーが httpOnly cookie のセッショントークンを Bearer に変えて api を呼ぶ。モバイルは `/api/*` を Bearer で直接呼ぶ。api（Hono）がビジネスロジックと DB アクセスの唯一の入口になる。唯一の例外が画像で、`<img>` は Authorization ヘッダを付けられないため、`GET /api/images/{imageId}` に限りブラウザが同一オリジンで cookie を送り、api がその cookie を受け付ける。DB は PostgreSQL、画像は非公開の S3 バケットに置く。

```
apps/web        Next.js。画面と BFF（cookie 付きセッションを Bearer に変換して api を呼ぶ）
apps/api        Hono。REST + OpenAPI、認証・認可、DB、画像、メール送信
packages/contract  zod スキーマ（リクエスト・レスポンス・エラー形式）。web と api が共有
infra/          AWS CDK（TypeScript）。本番の全リソース
```

認可の判定（誰がどの投稿を見られるか）は api の一箇所にまとめ、一覧・検索・単体ページ・画像で共通の条件を使う。

### データモデル

主キーは UUIDv7（時刻順）で、一覧のページングは id のキーセットで行う。

- `users`: id, name, email（小文字化して一意）, password_hash（argon2id）, email_verified_at, visibility（public / private）, following_count（フォロー中 + 申請中。上限5,000の判定用）, created_at
- `email_tokens`: ユーザー、種別（確認 / リセット）、ハッシュ化したトークン、有効期限、使用済み
- `sessions`: ユーザー、ハッシュ化したトークン、有効期限、最終利用
- `posts`: id, author_id, body, search_text（NFKC 正規化 + 小文字）, image_id, like_count, deleted_at。インデックスは `(author_id, id desc)`、`id desc`、`search_text` の pg_bigm GIN
- `images`: id（ランダム）, post_id, s3 キー, content_type, size
- `likes`: `(post_id, user_id)` 主キー。`user_id` のインデックス
- `follows`: `(follower_id, followee_id)` 主キー、status（accepted / pending）、created_at（申請またはフォローの日時）、accepted_at（承認またはフォロー成立の日時）。申請一覧は `created_at desc`、フォロワー一覧は `accepted_at desc` の順で、同値のタイブレークに `follower_id` を使う複合キーセットでページングする。インデックスは `(followee_id, status, accepted_at desc, follower_id)` と `(followee_id, status, created_at desc, follower_id)`。公開ユーザーへのフォローは申請なしで accepted になり、created_at と accepted_at が同値になる
- `rate_limits`: キー（種別 + IP またはメールのハッシュ）、ウィンドウ開始、回数。レート制限のカウンタを複数タスクで共有するための DB テーブル（Redis は使わない）

### 閲覧権限の条件

投稿を見られるのは、削除されておらず、かつ投稿者が公開、または閲覧者が投稿者本人か accepted のフォロワーである場合。公開範囲はユーザー行を参照するため、変更は過去の投稿を含めて即時に反映される。フォロー解除・フォロワーを外す操作・削除も同様に、次のリクエストから反映される。

- タイムライン: `follows.status = accepted` のフォロー先と自分の投稿のうち `deleted_at is null` のもの。pending は含めない
- グローバルフィード・検索・ユーザーページ: 上の閲覧権限の条件でフィルタ。ゲストは公開ユーザーの投稿のみ
- ユーザーページ API: 名前、公開範囲、閲覧者との関係（none / pending / accepted / self）、投稿の閲覧可否（`can_view_posts`）を返す。閲覧不可のときは投稿一覧を返さず、画面は「投稿が非公開」と表示する（US-6.3、6.7、6.9）。投稿が0件の場合と区別できる
- 非公開から公開への切り替え: 同一トランザクションで、そのユーザー宛ての pending を削除し、申請者の `following_count` を減らす
- フォロー上限: トランザクション内でフォローする側のユーザー行をロックし、`following_count` が5,000未満のときだけ追加する。`following_count`（accepted + pending の合計）は、フォロー、申請、解除、申請の取り消し、拒否、フォロワーを外す操作、公開化による申請の破棄の、すべてで同一トランザクション内で増減する
- 読み取り元: 閲覧権限の判定を含む読み取り（各一覧・検索・単体ページ・画像）と認証の読み取りは、常にプライマリを使う。規模が増えたときの増強はプライマリの垂直スケールとクエリ・インデックスの改善で行い、読み取りレプリカは使わない（レプリカの遅延で即時反映を破らないため）。レプリカにできるのは、権限判定を伴わない集計などに限る
- 書き込み系の認可: いいねは閲覧権限のある投稿にだけ成立する。削除は投稿者本人、承認・拒否・フォロワーを外す操作は対象の宛先が本人のものに限る。対象 ID は常に認証済みユーザーの文脈で引く（IDOR の防止）
- 権限が無い場合の応答: 単体ページ・投稿 API・画像は、権限が無い場合も存在しない場合も 404 で返す（存在を漏らさない）

### 認証・メール

ADR「認証は DB 保存の不透明トークンのセッションで行う」に従う。登録時に確認メール、パスワードリセット時にリセットメールを送る。トークンはハッシュ化して保存し、有効期限と使用済みを持つ。パスワードリセットの完了時は、そのユーザーの全セッションを失効させる。ローカルは Mailpit（SMTP）に届け、本番は SES を使う。メール送信は nodemailer の SMTP で共通化し、接続先を環境変数で切り替える。登録済みメールアドレスの有無が応答から分からないようにする（アカウント列挙の防止）。ただし US-1.2 により、登録は既存メールでも新しいアカウントを作らず、応答は同じ成功表示とし、既存の持ち主には通知メールを送る。パスワードは8文字以上とする。ログイン・登録・パスワードリセット要求・確認メール再送にはレート制限を設ける（IP とメールアドレスのハッシュ単位、カウンタは `rate_limits` テーブル）。確認メールの再送の応答も、アカウントの有無や確認状態が分からない内容にする。

### 投稿・検索・画像

投稿の作成時に、本文の検証（300文字以内、空白・改行のみは本文なしとみなす）、画像の検証（マジックバイトで JPEG / PNG / GIF / WebP を判定、5MB 以内、メタデータの無再エンコード除去）、`search_text` の生成を行う。検索は、入力を空白（全角含む）で分割し、`-` 除外、`OR`、`"..."` フレーズを解釈して LIKE の論理式に変換する（ADR「投稿検索は PostgreSQL の pg_bigm と正規化列で実装する」）。条件として成り立たない入力（除外のみなど）は 400 で返す。LIKE のメタ文字（`%` `_` `\`）はエスケープし、値は必ずパラメータ化する。

検索語の文字数・語数には、任意の上限を設けない。本文の300文字上限はクエリ全体の上限を意味せず、短い語を多数 OR で結ぶ検索や、20語を超える AND / OR も、US-10.6〜10.9 の範囲で有効な検索だからである。有効な検索を拒否する唯一の経路は、HTTP の転送上の限界（ALB のリクエストライン約16KB）と、後述の負荷保護で処理できなかった場合に限る。転送上の限界を超える長さの検索が必要になった場合に備え、検索は `GET` に加えて `POST /api/search`（本文にクエリ）でも受けられる設計とする。

検索の負荷は、入力を拒否せず次の方法で守る。

- 同じ語の重複を正規化後に除き、論理式を最小にする。AND は GIN の条件の積、OR は和として1回のインデックススキャンにまとめる
- 検索用に専用の小さな DB 接続プールを持ち、重い検索が他機能の接続を奪えないようにする
- 検索クエリに DB の `statement_timeout`（p95 3秒の目標に合わせた値）を設ける。超過したクエリは中断し、503 と「混み合っています。時間をおいて再度お試しください」を返す。これは容量による一時的な失敗であり、入力の内容で拒否するものではない
- 利用者・IP 単位のレート制限（`rate_limits`）を検索にも設け、同じ検索を連続して投げて DB を占有することを防ぐ
- ECS のオートスケールで api の処理能力を確保する

これらで要件（p95 3秒、有効な検索を受け付ける）を満たせるかは、検証計画の負荷試験で実測する（語数が数百の AND / OR を含む）。満たせない場合は、入力を制限して合わせるのではなく、満たせない条件と対策案を報告する。

画像は、5MB 以内であることに加え、受け入れ基準が定める JPEG / PNG / GIF / WebP であることをマジックバイトとヘッダの構造で検証する。画素数の上限は設けない（受け入れ基準が許す5MB以内の画像を、基準に無い理由で拒否しないため）。位置情報などのメタデータは、画像をデコード・再エンコードせずに除去する。画像の表示と動きを保つため、除去の対象と残すものは次のとおりに分ける。

- JPEG: APP1（Exif / XMP）、APP13（IPTC）、コメントを除去する。ただし EXIF の向き（Orientation）は、除去すると縦横が変わって表示されるため、向きだけを持つ最小の EXIF に書き換えて残す。JFIF、ICC プロファイル（APP2）、Adobe（APP14）は残す
- PNG: `tEXt` / `zTXt` / `iTXt` を除去し、`eXIf` は向きだけの最小の内容に書き換える。`iCCP`、`gAMA`、`cHRM`、`sRGB`、`pHYs` と、アニメーション用の `acTL` / `fcTL` / `fdAT` は残す
- WebP: EXIF / XMP チャンクを除去し、向きは最小の EXIF として残す。ICC（`ICCP`）、アニメーション（`ANIM` / `ANMF`）、`VP8X` のフラグは実際の内容と整合させる
- GIF: コメント拡張とプレーンテキスト拡張、XMP のアプリケーション拡張を除去し、アニメーションに必要なグラフィック制御拡張と、ループ回数を持つ `NETSCAPE2.0` 拡張は残す

デコードしないのでメモリは最大でも5MB程度の読み込みに収まり、画素数に依存しない。ヘッダを解釈できない画像は、形式不正として US-4.6 の理由表示（「対応していない形式、または壊れた画像です」）で拒否する。配信時の `Content-Type` は検出した型から出し、`X-Content-Type-Options: nosniff` を付ける。

画像は ADR「画像はリクエストごとに認可して配信する」に従う。S3 は全面的にパブリックアクセスをブロックし、`GET /api/images/{imageId}` が認可した上で S3 から読んで返す。

### 本番構成（AWS 東京リージョン）

- ECS Fargate に web と api の2サービス（各2タスク以上、複数 AZ）。ALB でパスを振り分ける
- RDS PostgreSQL（pg_bigm を有効化）。Multi-AZ で月間 99.9% を目標にする。バックアップとポイントインタイムリカバリを有効にする
- S3（画像）、SES（メール）、Secrets Manager、CloudWatch Logs
- 単体ページの急増はオートスケールで受ける（ADR「投稿データは CDN でキャッシュせず…」）。最小台数を保ち、CPU のスケール閾値は低めにする
- 費用は月額300米ドルが目安。Multi-AZ の RDS・NAT・ALB・Fargate の常時分で目安に近づくため、インスタンスサイズと NAT の構成は見積りで決め、収まらなければ報告する

### 品質・運用の基盤

テスト基盤（api は `app.request()` で呼べる単体・結合テスト、DB は実 PostgreSQL）、lint、CI（typecheck / test / build）、DB マイグレーション、構造化ログ、ヘルスチェック（`/health`）、README、OpenAPI 仕様書の生成を整える。

デプロイは GitHub Actions から、イメージのビルド、ECR への push、マイグレーションの one-off ECS タスク実行、ECS サービスのローリング更新の順で行う。マイグレーションは新旧のコードが同時に動く時間があるため、後方互換（追加してから切り替え、最後に削除する）に限る。運用の監視は CloudWatch アラーム（ALB の 5xx 率と応答時間、ECS のタスク数と CPU、RDS の CPU・接続数・空き容量）と、ALB ターゲットの `/health` 死活監視で行い、月間稼働率は ALB のメトリクスから算出する。

### 性能・費用の検証計画

1年後の規模のデータ（ユーザー10万、投稿500万、いいね5,000万、フォロー500万）を投入した DB に対し、負荷試験で次を実測する。結果が要件を満たさない場合は、満たせない理由と対策案を報告する（要件は緩めない）。

- 一覧・単体ページの p95 1秒、検索の p95 3秒、書き込みの p95 1秒（ピーク時の読み取り毎分500件、書き込み毎分50件）
- 単体ページに毎分5,000件が30分続く間の、表示の継続と他機能への影響。単体ページの表示ごとに画像の取得（認可 + S3 読み取り + 最大5MBの転送）も発生するので、画像つきの投稿を前提に試験する
- 画像リクエストごとの認可を含む配信の負荷（一覧由来で秒間約170件の目安）と、ECS・転送の費用見積り
- 検索の負荷保護の検証: 語数が数十から数百の AND / OR、短い語を多数 OR で結んだ長いクエリ、ヒット数が非常に多い語を含めて、p95 3秒と他機能への影響を実測する。入力の制限は設けない
- 画像のメタデータ除去の検証: JPEG / PNG / GIF / WebP のそれぞれで、除去後に（a）ブラウザで表示できる、（b）位置情報などの除去対象が残っていない、（c）EXIF の向きが回転ありの JPEG で正しく表示される、（d）ICC プロファイルがある画像の色が変わらない、（e）アニメーションの GIF（と WebP）が除去前と同じフレーム数・ループ回数で動く、ことをテストと目視で確認する。5MB 近い画像と、画素数が非常に大きい画像でも、メモリ使用量と処理時間が問題にならないことを確認する
- 画像配信が api を飽和させる場合は、同じコードのまま ALB のパスルール（`/api/images/*`）で画像配信専用の ECS サービスに分離し、それぞれ独立にスケールさせる。この分離を許す構成にしておく

## 永続ドキュメントの更新予定

- `overview` の新規作成: 全体構成、コンポーネントの責務、データフロー、認可の判定の置き場所
- `constraints` の新規作成: 性能目標、可用性、公開範囲の即時反映、画像の認可方針、費用の目安
- `decisions`: 今回追記した6件の ADR を `implemented` に更新（close-cycle）
- `conventions` の新規作成: ディレクトリ構成（`apps/*`・`packages/*`・`infra/`）、命名、エラー形式、テストの書き方
- `security-model`: 認証方式、認可の判定、画像配信、レート制限、アカウント列挙の防止（constraints に収まらなければ分離する）
- `db-schema` / `interfaces`: 参考。正はマイグレーションと OpenAPI

## 既存構造への影響

- `pnpm-workspace.yaml`: `packages/*`（と `infra`）を追加する
- `docker/Dockerfile.dev` と `compose.yaml`: パッケージの COPY を更新し、PostgreSQL（pg_bigm を含む）、Mailpit、マイグレーション実行、S3 互換ストレージ（ローカル用。MinIO など）を追加して、`docker compose up` の1コマンドで全体が起動するようにする
- `apps/api/src/app.ts`: ミドルウェアとルートの接続点。`app` を export する形は維持する
- `apps/web`: Next.js 16 の破壊的変更があるため、実装前に `node_modules/next/dist/docs/` の該当ガイドを読む。`cacheComponents` が有効なので、静的シェルと動的データの境界を明確にする
- 追加のみで既存の本番データは無いため、各ビルドをマージしても本番データを壊さない。未完成の機能は画面からの導線を出さないことで隠す
