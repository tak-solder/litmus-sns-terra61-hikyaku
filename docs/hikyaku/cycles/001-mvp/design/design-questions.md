# 設計段階の質問

Step 3 の独立した質問ラウンドは設けず、分岐のある判断（G3）の中で必要な確認を行った。回答は監督から委任された判断（人間ではなく監督が下した判断）である。

### Q1（G3 / D1）: 投稿検索の方式
**回答**: A（PostgreSQL + pg_bigm + NFKC 正規化列）を採用。

### Q2（G3 / D2）: タイムラインの生成方式
**回答**: A（読み取り時に生成）を採用。

### Q3（G3 / D3）: 認証方式
**回答**: A（DB 保存の不透明トークンのセッション）を採用。

### Q4（G3 / D4）: API 方式と Web との共有
**回答**: A（REST + OpenAPI、契約を `packages/*` で共有）を採用。

### Q5（G3 / D5）: 単体ページの急増への対策。削除と非公開化の反映遅延を許容するか
**回答**: 許容しない。案 B（CDN で投稿データをキャッシュせず、ECS のオートスケールと DB で受ける）を採用。
根拠: US-11.2、US-11.3、US-11.6、US-12.5 が公開範囲変更の即時反映と非公開投稿の閲覧制限を要求している。要件を緩める権限は委任されていない。性能と費用は実測・見積りで検証し、満たせない場合は報告する。

### Q7（G4 / 差し戻し）: 設計の承認
**回答**: 承認せず、次の修正を指示（委任された判断）。(1) タイムライン ADR の読み取りレプリカでの増強が、権限判定を含む読み取りを常にプライマリに限定する design-delta と矛盾するため、即時反映を保つ増強方法に直す。(2) 検索の文字数・語数や画像の画素数の上限は user-stories に無いため、受け入れ基準を満たすことの確認と、制限の根拠・利用者への表示を明示する。
根拠: design-delta の閲覧権限の読み取り元、planning/user-stories.md の US-10 と US-11.3。
対応: (1) タイムライン ADR を、プライマリの垂直スケールとクエリ・インデックス改善による増強に修正（レプリカは使わない）。(2) 検索語の上限は、本文300文字以内を根拠に、全体300文字・20語とし、超過時は 400 と画面表示を返す。画素数の上限は廃止し、デコードしないメタデータ除去に変更した。

### Q8（G4 / 差し戻し 2回目）: 検索上限の根拠
**回答**: 承認せず再修正を指示（委任された判断）。本文の上限は検索クエリ全体の上限を意味せず、短い語を OR で結ぶ検索や20語を超える AND / OR にも受け入れ基準上の制限は無いので、任意の上限で有効な検索を拒否しない設計にする。負荷の保護は要件を満たす方法を検討し、満たせない場合は報告する。画像のメタデータ除去は、JPEG / PNG / GIF / WebP の表示と GIF のアニメーションを保つことを検証計画に含める。
根拠: planning/user-stories.md の US-10.6〜10.9 と US-4 の対応形式。
対応: 文字数・語数の上限を廃止。重複語の除去、検索専用の接続プール、statement_timeout、レート制限、オートスケールで保護し、満たせなければ報告する。画像は向き・ICC・アニメーション用の情報を残す除去仕様と、表示・色・向き・アニメーションの検証項目を追加した。

### Q9（G4 / 承認）: 設計の承認
**回答**: 承認（委任された判断）。G3 の認可方針、プライマリ読み取り、検索上限の撤回、画像形式の検証計画が反映されていることを確認。性能・費用と画像処理の検証は設計書に従い、未達の場合は報告する。
根拠: design-delta と ADR の確認。

### Q10（G6 / ビルド分割の承認）: 33ビルドの分割
**回答**: 承認（委任された判断）。ただし、旧 build 10・11 が番号の大きい旧 build 14 に依存していたため「依存はすべて小さい番号」という説明は誤りと指摘された。依存先が存在する順序で登録できるよう、投稿の作成・削除（新 10）と投稿単体取得・閲覧権限（新 11）を、公開範囲・申請・フォロワー系（新 12〜14）より前に採番し直した。最終検証（build 32）は、評価に必要な画面のビルド（22〜27）すべてに依存させた。
対応: 33件を依存先が存在する順で登録し、循環が無いこと（登録時に CLI が検証）と、`validate` で受け入れ基準の割り当てと issue.md の整合に問題が無いことを確認した。
根拠: 分割はいずれも BP 5 以下で上限8以内。設計差分の認可・検索・画像・インフラ・負荷検証に対応し、危険なデータ移行は無い。

### Q6（G3 / D6）: 非公開ユーザーの画像を、推測不能 URL のみで秘匿してよいか
**回答**: 認めない。署名 URL（案 B）も、権限変更後に既発行 URL が使える間は即時反映を満たさないため不可。画像リクエストごとの認可など、権限変更を即時反映する方式を設計する。
根拠: Q5 と同じ。
