# タイムラインは読み取り時に生成する

- **決定**: タイムラインは、承認済みフォロー先と自分の投稿を `(author_id, id desc)` のインデックスで取得し、id のキーセットページングで続きを返す。配信用のテーブルは持たない。
- **文脈**: フォロー上限は5,000人、フォロワー数は無制限（5万人以上もいる）。1年後のピークは読み取り毎分500件、書き込み毎分50件。公開範囲の変更・フォロー解除・削除は即時に反映する必要がある。
- **検討した案**:
  - 案A: 読み取り時に生成（fan-out on read）
  - 案B: 書き込み時に各フォロワーのタイムラインへ配る（fan-out on write）
  - 案C: 案A と案B のハイブリッド
- **採用理由**: 読み取りは秒間10件弱と少なく、読み取り時の生成で p95 1秒を満たせる見込みが高い。承認済みフォローだけを対象にするため非公開の判定が構造的に満たされ、削除・非公開化・フォロー解除が即時に反映される。案B は5万フォロワーの投稿1件で5万行の書き込みが生じ、整合を保つ処理も増える。
- **トレードオフ**: フォロー先が5,000人の閲覧者ではクエリが重くなる。タイムラインは閲覧権限の判定を含む読み取りなので、即時反映（US-11.3、11.6）を保つため読み取りレプリカでは受けず、常にプライマリで実行する。規模が数倍になったときは、プライマリのインスタンスクラスを上げる垂直スケール、クエリとインデックスの改善、接続プールの調整で増強する。それでも足りなくなれば案Cへ移行する。案Cで配信テーブルを持つ場合も、表示時に閲覧権限をプライマリで再判定し、配信済みの行だけを根拠に表示しない。垂直スケールはインスタンスの変更時に短い切り替えが生じる（Multi-AZ のフェイルオーバー相当）。
- **影響範囲**: `follows` と `posts` のインデックス設計、タイムライン API。
