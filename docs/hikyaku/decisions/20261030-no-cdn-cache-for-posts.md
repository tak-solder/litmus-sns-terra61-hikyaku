# 投稿データは CDN でキャッシュせず、オートスケールと DB で急増を受ける

- **決定**: 投稿・一覧・単体ページのデータを CDN にキャッシュしない。単体ページへのアクセス急増（毎分5,000件が30分）は、ECS のオートスケールと PostgreSQL の主キー参照で受ける。Next.js は静的なシェルだけを事前生成し（Partial Prerendering）、投稿データは毎回取得する。
- **文脈**: 単体ページの急増に耐えつつ、常時コストは最小にしたい。一方で US-5.2（削除した投稿は表示されない）、US-11.3（公開範囲の変更は即時に反映）、US-11.6、US-12.5 は削除と公開範囲の変更の即時反映を要求している。
- **検討した案**:
  - 案A: CloudFront で公開投稿を `s-maxage` 付きでキャッシュし、削除・非公開化の際に無効化する
  - 案B: キャッシュせず、ECS のオートスケールと DB で受ける
  - 案C: 全投稿を静的生成する
- **採用理由**: 案A と案C は、CDN に古い内容が残る間（無効化の伝播に数十秒から数分）、削除と非公開化が反映されない。要件は即時反映なので、緩めない。単体ページの読み取りは主キー参照が中心で、毎秒83件程度なら PostgreSQL の負荷としては小さい。
- **トレードオフ**: 急増に対するスケールを CDN ではなく計算資源で受けるため、急増の立ち上がりでオートスケールが追いつくまでの間は余力（最小台数と低めのスケール閾値）に頼る。急増時は台数が増え、その時間分の費用がかかる。この性能は実測で検証する（ビルドで負荷試験を行い、満たせなければ報告する）。
- **影響範囲**: `apps/web` のレンダリング方式（静的シェル + 動的データ）、ECS サービスのオートスケール設定、単体ページ用の API とクエリ。
