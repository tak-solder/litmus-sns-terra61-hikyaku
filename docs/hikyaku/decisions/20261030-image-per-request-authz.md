# 画像はリクエストごとに認可して配信する

- **決定**: S3 バケットは非公開にする。画像は API の `GET /api/images/{imageId}` で配信し、リクエストのたびに閲覧権限（投稿が存在するか、投稿者が公開か、閲覧者が本人またはフォロワーか）を判定して、S3 から取得した内容を返す。署名 URL は発行しない。応答は `Cache-Control: private, no-cache` と ETag（画像 ID 由来）とし、ブラウザは再検証のたびに認可を受けて、権限があれば 304 でバイト転送なしに済ませる。認証は Bearer に加えて、この GET に限り同一オリジンの session cookie を受け付ける。
- **文脈**: US-11.2・11.3・11.6・12.5 により、公開範囲の変更・フォロー解除・投稿削除は即時に反映する必要がある。画像も例外ではなく、非公開ユーザーの画像が URL を知る第三者に見えてはならない。
- **検討した案**:
  - 案A: 推測不能なキーのまま CloudFront で署名なし配信する
  - 案B: 署名付き URL / Cookie で配信する
  - 案C: 署名 URL を短命にして一覧のたびに発行し、直接アップロードも併用する（presigned）
  - 案D: API がリクエストごとに認可して配信する
- **採用理由**: 案A は URL が漏れたら取り消せない。案B・案C は、権限が変わったあとも発行済みの URL が有効な間は見えてしまい、即時反映を満たさない。案D だけが、権限変更の直後から次のリクエストで拒否できる。画像の実体検証と EXIF 除去を API で行う前提とも一致する。
- **トレードオフ**: 画像のバイトが API の ECS タスクを通るため、CPU・帯域・データ転送費が増える。1年後の画像リクエストは一覧の画像数に比例し（読み取りピーク毎分500件 × 最大20枚で秒間約170件が上限の目安）、1件ごとに認可クエリが1〜2回走る。CDN の配信は使えず、他のキャッシュ層でも権限の判定を省けない。取得済みのバイトがブラウザに残るのは避けられない。これらの性能と費用は実測と見積りで検証し、満たせなければ報告する。
- **影響範囲**: `apps/api` の画像配信ルートと認可クエリ、S3 バケット設定（パブリックアクセスを全面ブロック）、認証ミドルウェア（cookie の許可範囲）、ECS タスクの IAM（S3 読み書き）。
